# Gamlish Threat Model

## Scope and assumptions

The system is a browser-based learning application with a Next.js frontend, Express API, Prisma ORM, and MySQL. Roles are `student` and `admin`. The database stores accounts, lessons, questions, options, progress, and quiz attempts. The following are realistic threats for this lab.

| Threat | Impact | Mitigation |
|---|---|---|
| Credential stuffing or repeated login attempts | Account takeover; unauthorized student or admin access | Add rate limiting, monitoring, MFA for provider/admin accounts, generic login errors, and strong unique passwords. |
| JWT stolen from browser storage | Attacker can impersonate the user until expiry | Prevent XSS, prefer Secure HttpOnly SameSite cookies for production, shorten token lifetime, rotate and revoke tokens, and never log tokens. |
| JWT secret left at the configured fallback | Anyone who obtains the fallback can forge tokens, including admin claims | Require a long random `JWT_SECRET` in production and fail closed when it is absent. |
| Forged or modified role claim | Privilege escalation to admin | Verify JWT signature and claims, derive sensitive authorization from trusted server state where appropriate, and test student access to every admin route. |
| Broken object-level authorization using another user's ID | Exposure or alteration of progress and quiz attempts | Derive user ID from the authenticated principal and check ownership on every object read or write. |
| Student reaches admin CRUD endpoint | Lesson, question, or user data manipulation | Keep `authenticate` and `requireAdmin` on the entire admin router and verify with negative tests. |
| SQL injection in IDs, filters, or future search fields | Data disclosure, data modification, or database compromise | Use Prisma parameters and `Prisma.sql`; never concatenate input into SQL; validate types and allowlist dynamic identifiers. |
| Stored XSS in lesson, question, name, or option content | Script execution in other users' browsers; token theft | Escape output by default, avoid unsafe HTML rendering, validate URL schemes/hosts, and deploy CSP/security headers. |
| Reflected XSS through error or query content | Script execution in a victim's browser | Keep error messages server-generated, encode output, and test special characters in all reflected views. |
| Malicious or unexpected video URL | Phishing, unsafe embeds, or external tracking | Validate URL scheme and approved host policy; use privacy-conscious embeds and review redirect behavior. |
| Excessive request body or quiz payload | Resource exhaustion or slow API responses | Keep body limits, validate array lengths and string sizes, add rate limits, and monitor request latency. |
| Admin account compromise | Full access to users, lessons, questions, progress, and scores | Strong admin credentials, MFA at provider level, short sessions, audit logging, least privilege, and review of admin activity. |
| Database credential or backup exposure | Disclosure of all users and learning records | Secret manager, TLS, least-privilege DB user, restricted network access, encrypted backups, and rotation procedures. |
| CORS misconfiguration or permissive origin reflection | Cross-origin abuse of APIs and higher exposure to browser attacks | Configure an explicit production allowlist and verify preflight and credential behavior. |
| Sensitive error or log disclosure | Leakage of schema, infrastructure, hashes, tokens, or personal data | Return generic 4xx/5xx messages, protect logs, redact fields, and alert without sensitive payloads. |
| Public demo account reuse | Unauthorized access to seeded data or admin functions | Rotate or remove demo credentials before real deployment and keep them out of documentation and screenshots. |
| Unreviewed dependency or deployment compromise | Malicious code execution or data theft | Lockfile review, dependency scanning, MFA, protected branches, restricted CI secrets, and controlled releases. |

## Trust boundaries

1. Browser to frontend: user-controlled input and client storage are untrusted.
2. Frontend to API: headers, body, path, and query values are untrusted even when generated by the UI.
3. API to database: only the backend should hold database credentials and construct queries.
4. Deployment providers: Vercel, Render, and Aiven accounts and secret stores are administrative trust boundaries.

## Highest-priority risks

1. Require the production JWT secret and remove reliance on the fallback.
2. Replace permissive CORS with an exact origin allowlist.
3. Address the risk of JWTs in `localStorage` through XSS hardening and a cookie-based session design.
4. Verify object-level authorization for student progress, attempts, and results.
5. Add rate limiting and audit visibility for authentication and administration.
